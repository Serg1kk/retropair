# Оркестрация ревью: брифы, стабы, перезапуск, коды выхода

> Справочник скилла `review` к фазам 3–12. Поля входа агентов и их выход определяет
> [judge-input.md](judge-input.md); здесь — как скилл собирает эти поля из вывода команд,
> как ставит задачу агенту и что делает при каждом коде выхода.

Обозначения: `<plugin_root>` — абсолютный корень плагина (если в пути виден литерал
`${CLAUDE_PLUGIN_ROOT}`, это папка два уровня выше `skills/review/SKILL.md`); `<ws>` —
абсолютный путь к `.sessionretro/` проекта; `<pending>` — `<ws>/runs/pending/<person>`.
Все пути во входе агента абсолютные.

## Стабы

До запуска агента скилл сам создаёт его файл выхода через Write. Содержимое стаба одно для
всех ролей:

```json
{"stub": true}
```

| Роль | Файл | Когда создаётся |
|---|---|---|
| коллектор | `<pending>/batch-NN.json` (NN = `batch.index`, две цифры) | фаза 3, по файлу на пачку |
| судья | `<pending>/judge.json` | фаза 3 |
| критик | `<pending>/critic.md` (стаб — строка `stub`), черновик `<pending>/draft.md` | фаза 10, только если критик зовётся |

Агент читает стаб и перезаписывает его целиком: через Edit или перезаписью `output_path`.
Других файлов он не создаёт. Стаб, оставшийся стабом после ответа агента, скрипты ловят сами:
`check-collector` и `append` отвечают кодом `1` «стаб не заполнен», `verify` стабы сиротами
не считает.

Записанный выход судьи прошлого прогона остаётся в `<pending>/judge.json` (он нужен
`render-review`) и вопроса не стоит: в фазе 3 файл перезаписывается стабом. Незаписанный
отличает `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" verify`: его sha256 нет ни в одном прогоне трекера, и `verify` печатает
строку `сирота: … runs/pending/<person>/judge.json`. Только про сироту скилл спрашивает,
записать ли её (при `--no-ask` прогон по человеку останавливается).

## Бриф коллектора

Один вызов Agent на пачку; все пачки человека — одним сообщением. `subagent_type` и `model` —
по таблице «Выбор агента» в `SKILL.md`. Текст задания:

```text
Ты первая ступень оценки. Прочитай свой промпт и вход ниже. Баллов не ставь.
Прочитай стаб output_path и перезапиши его целиком одним JSON по схеме
<plugin_root>/references/schemas/collector.json. Других файлов не создавай.
В ответ не больше десяти строк сводки: run_id, output_path, что прочитано, предупреждения.
Нет обязательного поля во входе → ничего не пиши и первой строкой назови поле.

ВХОД:
<JSON ниже>
```

Как собирается вход из вывода команд:

| Поле | Откуда |
|---|---|
| `plugin_root` | корень плагина |
| `workspace_root` | `<ws>` |
| `workspace_id` | `workspace.id` из `<ws>/config.json` |
| `person_id` | id карточки |
| `period` | `{label, from, to, anchor}`: `label` — метка прогона (в режиме `run` плановая `run-<ГГГГММДД>`: настоящую выдаёт `append`, у второго прогона за сутки она с суффиксом `-2`); `from`/`to` — `date_from` первой и `date_to` последней пачки (`ГГГГ-ММ-ДД`) или `null`; `anchor` — `null`, если пользователь не назвал опорную точку |
| `run_id` | плановый id из фазы 1 |
| `lang` | `lang` из `config.json` |
| `output_path` | `<pending>/batch-NN.json` этой пачки |
| `log_paths` | по сессии пачки: `path` = `<ws>/` + `sessions[].path`, `session_id`, `state`, `from_turn` (у `grown` обязателен) |
| `batch` | `{index, total}` из `batches[]` |
| `task_summary` | аргумент `--task-summary`, ответ пользователя или «нет» |
| `open_recs` | только `open` из `open-recs <person> --json --period-label <label>` (в режиме `run` без `--period-label`): `id`, `text`, `period`, `issued_at`, `evaluable` как есть. `evaluable` считает скрипт по сессиям периода, законченным после `issued_at`; `false` → судья ставит `not_applicable_yet`, коллектор сигналов по ней не собирает. `pending_approval` (рекомендации неодобренного черновика при `reviewer_gate: true`) агентам не подаётся: человек их не получал, вердикт отложен до `approve` и идёт строкой в сводку |
| `context_report` | `null`: отдельной сводки по окну сбор логов не строит (коллектор пишет `no_context_report`); пик контекста, доля кэша и компакты сессий Claude Code — поля `context_peak_tokens`, `cache_share`, `compactions` в `metrics` записи `inventory --json` |
| `repo_path` | в режиме self — корень проекта (`workspace` из `doctor --json`); иначе `null`, если пользователь не назвал репозиторий |
| `show_scores` | `show_scores` из `config.json` |

`card_slice` коллектору не подаётся никогда.

## Бриф судьи

Один вызов Agent на человека, после зелёного `check-collector`. Текст задания тот же, что у
коллектора, со схемой `<plugin_root>/references/schemas/judge.json` и без запрета на баллы.
Вход — общие поля коллектора без `batch`, плюс:

| Поле | Откуда |
|---|---|
| `output_path` | `<pending>/judge.json` |
| `log_paths` | все сессии всех пачек прогона, для точечной сверки цитат |
| `collector_outputs` | абсолютные пути `<pending>/batch-NN.json` в порядке `batch.index` |
| `excluded_sessions` | `short[]` → `{session_id, path: <ws>/…, status: "transcript_too_short", status_note: null}`, `skipped[]` → то же со статусом `other_period`; нет таких → `[]`. Сессии `other_period` в индексе не закрываются: `append` оставляет их открытыми для прогона своего периода |
| `sessions_total` | сессии человека за период: во всех пачках плюс `short[]` плюс `skipped[]` |
| `card_slice` | вывод `people context <person>` строкой. Карточка обязательна: без неё прогон по человеку остановлен ещё в фазе 1 |
| `next_rec_number` | `next_number` из `open-recs <person> --json`: следующий свободный номер с учётом отозванных и закрытых рекомендаций |

В конец текста задания судье, перед `ВХОД:`, добавляется строка (`NNN` — `next_rec_number`
тремя цифрами, например `REC-alex-004`):

```text
номер новой рекомендации начинать с REC-<person>-<NNN>
```

По `open_recs` следующий номер не вычислить: номера отозванных прогонов и закрытых
рекомендаций туда не входят, но заняты навсегда. Взял судья другой номер — `append` всё равно
перенумерует новые рекомендации подряд со свободного и предупредит строкой «рекомендации
перенумерованы: …» в `warnings`; судья из-за этого не перезапускается.

Список того, что судье не подаётся, — в `SKILL.md`, раздел «Что не подаётся судье».

## Бриф критика (необязательно)

Только в режимах team и course и без `--no-ask`, после зелёного `render-review`. Скилл
копирует отправляемый блок файла ревью (между первой и второй строкой `---` после служебного
блока) в `<pending>/draft.md`, создаёт стаб `<pending>/critic.md` и зовёт критика с входом:
`plugin_root`, `lang`, `draft_path` = `<pending>/draft.md`, `card_slice` как у судьи,
`output_path` = `<pending>/critic.md`. Таблица замечаний критика показывается ревьюеру рядом с
текстом; текст она сама не меняет.

## Перезапуск

Когда: `check-collector` отдал `1` по файлу (ремонтопригодные цитаты — сдвиг хода на
единственный ход человека, склейка кусков одной реплики без «…» — он чинит сам, это `0` и не
повод для перезапуска); после ответа файл остался стабом; агент назвал
недостающее поле; `append` отдал `1` по схеме или проверкам; `render-review` отдал `1` по
запретам текста.

Как:

1. Причина во входе (поле не подано, путь не тот) → поправить вход. Причина в выходе →
   вход тот же, в конец задания добавить блок «Прошлый выход отклонён проверкой:» и вывод
   команды дословно, без пересказа.
2. Вернуть стаб `{"stub": true}` в `output_path` и запустить агента заново.
3. Не больше двух перезапусков на агента. Третий отказ → прогон по человеку останавливается,
   в сводке команда, код и вывод; следующий человек из `--all` идёт дальше. Исключение —
   коллектор, у которого после двух перезапусков остались только несверенные цитаты (лог
   найден): `check-collector --drop-invalid` убирает эти записи, и прогон идёт к судье (фаза 5
   `SKILL.md`); `1` от него — стоп по человеку, как при третьем отказе.

JSON руками не правится никогда: ни чтобы пройти схему, ни чтобы убрать запрещённое слово.
Отказ проверки означает сбой ступени, а правка руками его прячет.

Выход судьи отклонён после записи (например, `render-review` нашёл запрет в тексте) →
перезапуск судьи, затем `append <pending>/judge.json --person <person> --replace <run_id>`,
`level`, `render-review`. Прогон оказался чушью целиком → `retract <run_id> --why "…"`:
прогон помечается недействительным, пометки логов откатываются.

## Коды выхода

`0` — ок; `1` — данные или проверка; `2` — неверный вызов. Что делать скиллу:

| Команда | `1` | `2` |
|---|---|---|
| `doctor` | — | неверный вызов. Код `0` с `"workspace": "не найден"` → workspace нет: предложить скилл `setup`, прогон не начинать |
| `agents` | `sync`: `agents.json` битый или файл агента не читается — показать вывод, прогон не начинать. Правленый вручную файл — не ошибка (код `0`, строка в сводку) | неверный вызов или workspace не найден |
| `collect` | сбор упал (источник, санитайзер) или замок сбора занят другим процессом дольше 10 с: показать вывод, прогон не начинать | неверный вызов или workspace не найден |
| `inventory` | индекс не собрался (конфиг `period`, битый индекс) или замок сбора занят: показать вывод, повторить после сбора или предложить `collect` | неверный вызов или workspace не найден: предложить скилл `setup` |
| `people` | — | карточки нет: остановить прогон по человеку до коллекторов (`append` без карточки не пишет), в сводке `sr.py people add <person>` |
| `open-recs` | трекер не читается: показать вывод, прогон остановить | карточки нет: остановить прогон по человеку |
| `batches` | замер упал на файле (путь в выводе): проверить `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" normalize <лог> --stats`, сказать пользователю; `--measure index` только с его согласия | неверный вызов |
| `check-collector` | кривые файлы: перезапуск этих коллекторов; после двух перезапусков с одними несверенными цитатами — `--drop-invalid`, его `1` — стоп по человеку. Ремонт цитат (`repaired`) и опущенный массив, дописанный пустым (`filled`), — код `0`, не повод перезапускать | файлов нет: проверить пути и стабы |
| `append` | схема или проверки: перезапуск судьи со списком. «id рекомендации … уже выдан» больше не приходит: занятый или не следующий номер `append` перенумеровывает сам (код `0`, строка «рекомендации перенумерованы» в `warnings`), судью не перезапускать; код `1` по рекомендации — только неверная форма id, чужой `person_id` или повтор в прогоне. «вердикт REC-… заменён: логи периода старше выдачи» — код `0`, вердикт заменён на `not_applicable_yet`, судью не перезапускать, строка в сводку. «REC-… из неодобренного черновика»: во вход судьи попал `pending_approval`, вход собрать заново только из `open` и перезапустить судью. «Уже есть прогон … с меткой»: повтор того же периода — `--replace <run_id>` из сообщения, новый период — другая метка (в режиме `run` метку не передавать, её выдаёт `append`) | карточка, метка периода или файл: поправить вызов |
| `mark-logs` | сессии не нашлись, покрытие неполное или явная ссылка спорит с уже поставленной пометкой: сверить ссылки, перепометить весь прогон `--force`. С `--no-run`: сессия не нашлась у этого человека (ничего не помечено) или уже помечена: сверить ссылки с `short[]` | неверный вызов, неизвестная причина или `other_period` в `--excluded`, сессия указана дважды (`--sessions`/`--excluded` принимают список, флаг можно повторять — ссылки копятся); с `--no-run` — id прогона, `--sessions` или `--force` рядом, нет `--person`, причина не из `transcript_too_short`, `empty_transcript`, `unreadable_input` |
| `level` | прогона нет или отозван: сверить `run_id` из `append` | неверный вызов |
| `render-review` | запреты текста или sha256 файла не совпал: перезапуск судьи, `append --replace` | шаблон с недопустимым именем или неверный вызов |
| `verify` | прогон закрыт не до конца: выполнить команды из вывода, повторить | неверный вызов |
| `approve` | нет файла ревью, прогон чужой или отозван | неверный вызов |

Ошибка любой команды печатается одной строкой `sessionretro: <что упало>: <почему> (<параметры>)`;
в сводку она идёт дословно.

## Сводка

По строке на человека, без оценок и уровней (в режиме self — только при `show_scores`), без
сравнений между людьми:

```text
<person> · <period_label из append> · <run_id>
  сессий оценено N, исключено K (коротких A, прочих C), другого периода B (ждут свой прогон) · пачек P
  текст: <ws>/reviews/<person>/<run_id>.md · статус draft|approved
  предупреждения: <warnings из append и render-review или «нет»>
  пачка неполная: <строки filled из check-collector, если есть>
  цитаты исправлены: <строки repaired из check-collector, если есть>
  наблюдения отброшены: <строки dropped из check-collector --drop-invalid, если есть>
  дальше: прочитать и одобрить /sessionretro:review --approve <person>
```

Если у человека `pending_approval` из `open-recs` не пуст, в его блок добавляются строки
`предупреждение: у <person> неодобренный черновик прошлого периода` и по одной на рекомендацию
`REC-… из неодобренного черновика <период> — вердикт отложен`. Прогон это не блокирует, при
`--no-ask` тоже: вердикт по этим рекомендациям вынесет прогон после `approve` черновика.

Для остановленных: `<person> · остановлен на фазе F: <команда>, код, вывод`. Для людей без
новых логов: `<person> · новых логов нет`. Для людей, у кого за период только короткие сессии
(закрыты `mark-logs --no-run`): `<person> · <метка> · за период только короткие сессии (N),
оценки нет — данных мало`. Строки «обновлён» и «правлен вручную» из `agents sync` (фаза 1) —
одной строкой `агенты: <строки через «; »>` перед итогом. Последней строкой — итог `verify`.

# Ретро периода: оценка по логам сессий

Скилл ведёт один прогон оценки на человека за период: разведка логов, нарезка на пачки,
первая ступень (коллекторы собирают факты и цитаты, баллов не ставят), вторая ступень (судья
ставит оценки только под цитату и пишет части текста), запись в трекер, уровень по формуле,
текст ревью по шаблону и сверка. Всё состояние живёт в `.sessionretro/` проекта. Скилл
координирует: сам логи не оценивает и JSON агентов не правит.

Брифы агентов, образец стаба, перезапуск и коды выхода каждой команды —
[references/orchestration.md](references/orchestration.md). Контракт входа агентов (поля,
выход, проверки) — [references/judge-input.md](references/judge-input.md).

## Как звать скрипты

Каждая команда вызывается ровно так: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" <команда> …`.
Если в пути остался литерал `${CLAUDE_PLUGIN_ROOT}` (хост его не подставил), корень плагина —
папка два уровня выше этого `SKILL.md` (`skills/review/SKILL.md` → корень); подставь её
абсолютный путь. Команды сами ищут `.sessionretro/` вверх от текущей папки; иначе добавь
`--workspace <корень проекта>`. Коды выхода у всех команд: `0` ок, `1` данные или проверка,
`2` неверный вызов. Ошибка печатается в stderr одной строкой: что упало, почему, с какими
параметрами.

Ниже `<ws>` — абсолютный путь к `.sessionretro/` проекта, `<pending>` — `<ws>/runs/pending/<person>`.

## Аргументы

`<person|--all> [--task-summary "…"|--no-ask] [--approve <person> [run]]`

| Аргумент | Что делает |
|---|---|
| `<person>` | id карточки человека (`people/<id>.yaml`): прогон по нему одному |
| `--all` | прогон по каждому, у кого есть логи `new` или `grown`; у кого их нет, прогона нет |
| `--task-summary "…"` | нейтральная строка о том, над чем шла работа, со слов пользователя, без критериев приёмки. Подаётся обеим ступеням |
| `--no-ask` | ни одного вопроса пользователю (для `claude -p`): `task_summary` = «нет», метка периода выводится (фаза 1), критик не зовётся. Где без вопроса дальше нельзя, прогон по человеку останавливается с явной причиной в сводке, а не идёт на значении по умолчанию |
| `--approve <person> [run]` | только одобрить готовый текст ревью: фазы 1–12 не выполняются (см. ниже) |

Без `--no-ask` вопросов не больше двух: `task_summary` одной строкой, если его не дали, и
подтверждение, если найден невыписанный выход судьи прошлого прогона (фаза 3).

**Одобрение.** `--approve <person> [run]` выполняет одну команду и выходит:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" approve <person> <run_id>
```

Без `run` одобряется последний живой прогон человека. Уже одобренный → код `0` и сообщение,
нет файла ревью → `1`.

## Правила

- **Ничего не срезать.** Пачка — разбиение, а не выборка: оцениваются все годные сессии
  периода, просто разными коллекторами. Сессии не делятся между пачками.
- **Две ступени всегда**, даже при одной пачке: сначала коллектор, потом судья. Оценка,
  полученная чтением сырого лога, и оценка из сведения фактов лежат на разных шкалах; путь
  один для всех, иначе рост человека не отличить от разницы в конвейере.
- **Стабы заранее.** Файл под выход каждого агента скилл создаёт сам до его запуска
  (`{"stub": true}`), и агент пишет в него через Edit или перезаписью `output_path`. Новый
  файл агенту создать могут не дать; без стаба он отработает и не сможет положить результат.
- **Ломаный JSON руками не правится** — перезапуск агента с той же постановкой и списком
  замечаний. Правка руками прячет сбой ступени: коллектор, который оценивал, подбирал цитаты
  под свою оценку.
- **`append` не откладывается.** Пока прогона нет в трекере, логи остаются новыми и поедут
  на повторную оценку, рекомендации не попадут в следующий период, а точки на графике нет.
- **Принципы оценки не меняются в скилле:** нет поведения в логе → «мало данных», а не низкая
  оценка; оценка только под цитату; профиль меняет формулировку, не оценку; оценки и уровни
  адресату не показываются (в режиме self только при `show_scores`); людей между собой не
  сравнивать нигде, в сводке по `--all` тоже; логи добровольны: нет логов — нет ни текста,
  ни вывода о человеке.

## Выбор агента

Для каждой роли скилл смотрит в проект:

| Роль | Файл в проекте | Без него | Модель |
|---|---|---|---|
| коллектор | `.claude/agents/sessionretro-log-collector.md` | `sessionretro:log-collector` | `config.models.collector.model` |
| судья | `.claude/agents/sessionretro-log-judge.md` | `sessionretro:log-judge` | `config.models.judge.model` |
| критик | `.claude/agents/sessionretro-feedback-critic.md` | `sessionretro:feedback-critic` | `config.models.critic.model` |

Файл в проекте есть → `subagent_type` = значение `name` из его frontmatter (проектная копия
промпта, которую пользователь мог поправить). Нет → плагинный агент из колонки «Без него».
`model` для вызова Agent берётся из `config.models` workspace (`config.json`). Коллекторы
запускаются **одним сообщением параллельно**: несколько вызовов Agent в одном ответе.

## Входы агентов

Полный контракт — `references/judge-input.md`. Кто что получает:

| Поле | Коллектор | Судья |
|---|---|---|
| `plugin_root`, `workspace_root`, `workspace_id`, `person_id`, `lang` | да | да |
| `period{label,from,to,anchor}`, `run_id` | да | да |
| `output_path` | стаб своей пачки `<pending>/batch-NN.json` | стаб `<pending>/judge.json` |
| `log_paths[]` | логи своей пачки целыми сессиями | все логи прогона, для точечной сверки цитат |
| `batch{index,total}` | да | нет |
| `collector_outputs[]` | нет | выходы всех пачек, прошедшие `check-collector` |
| `excluded_sessions[]`, `sessions_total` | нет | да |
| `card_slice` | нет | да |
| `task_summary`, `open_recs[]` | да | да |
| `context_report`, `repo_path`, `show_scores` | да | да |

Профиль (`card_slice`) коллектору не подаётся сознательно: текст пишет судья, а коллектор,
знающий грейд, начинает подгонять чтение под него.

## Что не подаётся судье

- прошлые баллы и уровни человека, прошлые оценки по осям: увидев старую оценку, агент
  подгонит новую, и динамика станет самоподтверждающейся (профессиональный грейд из карточки
  подаётся, наша прошлая оценка нет);
- внутренние суждения ревьюера о человеке: заметки, риски, впечатления от встреч;
- критерии приёмки задачи и то, что человек «должен был» сделать: `task_summary` только
  нейтральной строкой;
- оценка артефакта (кода, отчёта, PR): это другой проход;
- содержимое CLAUDE.md / AGENTS.md проекта: качество файла правил не материал логов;
- логи и тексты других людей.

## Фаза 1. Разведка

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" doctor --json
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" inventory --json
```

- `doctor --json` → поле `workspace` (корень проекта; `<ws>` = он плюс `/.sessionretro`) и
  `mode`. `"workspace": "не найден"` → предложить скилл `setup` и остановиться. Прочитай `<ws>/config.json`: `workspace.id`, `lang`, `period`, `models`, `batches`,
  `show_scores`, `reviewer_gate`.
- Проектные агенты — после `doctor`, строго до выбора агента по таблице ролей («Выбор агента»):

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" agents sync
```

  Копии в `.claude/agents/`, которые пользователь не правил, догоняют промпт текущей версии
  плагина; правленые не трогаются. Код `0` и при правленых. В выводе есть «обновлён» или
  «правлен вручную» → показать эти строки пользователю как есть и продолжать; при `--no-ask` не
  спрашивать, а положить их одной строкой в сводку (фаза 12). Код `1` → показать вывод, прогон не
  начинать.
- `inventory --json` → записи индекса логов. Кандидаты — записи человека в состоянии `new`
  или `grown`. Индекс пуст (`logs: []`) → остановиться и сказать
  собрать логи: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" collect`.
- Кандидатов у человека нет → прогона нет, в сводке «новых логов нет». Логи добровольны: это
  не вывод о человеке.
- Метка периода: `config.period.mode` `labels` или `dates` → метки из `period_guess` кандидатов;
  несколько меток → отдельный прогон на каждую, от старой к новой. Режим `run` или метки нет →
  метку не придумывай и в `append` не передавай: в режиме `run` её выдаёт сам `append`
  (`run-<ГГГГММДД>` по дате UTC, второй прогон за сутки получает `-2` и становится своим
  периодом), итог — поле `period_label` в выводе `append`. Для планового `run_id` и входа
  агентов бери `run-<ГГГГММДД>` по дате запуска. Во всех случаях `--period-confidence inferred`;
  `explicit` — только если метку назвал пользователь.
- Карточка и рекомендации человека:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" people context <person>
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" open-recs <person> --json
```

  `people context` → `card_slice`; `open-recs` → `open_recs[]` (`id`, `text`, `period`) для
  обеих ступеней, только из `open`, и `next_number` для судьи (`next_rec_number`: номера отозванных и закрытых
  рекомендаций заняты, по `open_recs` следующий номер не вычислить). `pending_approval` (team и course при `reviewer_gate: true`)
  — рекомендации неодобренного черновика: человек их не получал, агентам они не подаются,
  вердикт по ним отложен до `approve`, а номер занят. Не пуст → в сводку по строке
  «REC-… из неодобренного черновика <период> — вердикт отложен» и предупреждение
  «у <person> неодобренный черновик прошлого периода»; без `--no-ask` то же сказать
  пользователю до коллекторов. Прогон не блокируется, при `--no-ask` тоже. Код `2` у `people context` (карточки нет) → прогон по человеку
  останавливается, в сводке «нет карточки: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" people add <person>`». Без карточки `append`
  прогон не пишет, и коллекторы с судьёй отработали бы впустую.
- `task_summary`: из `--task-summary`; не дан → один вопрос пользователю; при `--no-ask` «нет».
- Плановый `run_id` = `<workspace_id>_<person>_<метка>_<ГГГГММДДTччммссZ>` по времени старта:
  агенты называют его в сводке. Настоящий id выдаёт `append` в фазе 7, дальше работай с ним.

## Фаза 2. Пачки

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" batches <person> --json --period-label <label>
```

Выход: `batches[]` (`index`, `total`, `sessions[]` с `path` относительно `<ws>`, `session_id`,
`state`, `from_turn`), `short[]` (короче порога, в пачки не идут), `skipped[]` (чужой период).
В режиме `run` (метка `run-<ГГГГММДД>`) `batches` зовётся без `--period-label`: такая метка не
совпадёт ни с одной `period_guess`, и все сессии с угаданным периодом ушли бы в чужой.
Бюджеты пачки — `config.batches` (`max_bytes`, `max_user_turns`, `min_turns`); размер меряется
по репликам человека через `normalize`. Код `1` → замер упал на файле (путь в выводе):
сказать пользователю; `--measure index` (грубый замер по размеру файла) только с его согласия,
при `--no-ask` прогон по человеку останавливается. Пачек ноль → прогона нет, агентов не зови:

- `batches[]` пуст, `short[]` не пуст → за период только короткие сессии. Закрой их все одним
  вызовом, иначе они останутся `new` и следующий `review` подберёт их снова:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" mark-logs --no-run --person <person> --excluded <session_id_1>=transcript_too_short <session_id_2>=transcript_too_short
```

  (по ссылке `<session_id>=transcript_too_short` на каждую сессию из `short[]`, все списком после
  одного `--excluded`; флаг можно повторять, ссылки копятся; одна ссылка дважды → код `2`). В сводке строка
  «за период только короткие сессии (N), оценки нет — данных мало». Это не вывод о человеке.
- `batches[]` и `short[]` пусты (остались сессии чужого периода) → в сводке «новых логов нет»
  за этот период, сессии из `skipped[]` ждут прогон своего периода.

## Фаза 3. Стабы

Создай папку `<pending>` и в ней, через Write, файлы с содержимым `{"stub": true}`:
`batch-01.json` … `batch-NN.json` (номер = `batch.index`, две цифры) и `judge.json`.
Старые `batch-*.json` перезаписываются стабами. Лежит непустой `judge.json` без `"stub"` →
сверить, записан ли он:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" verify
```

Строка `сирота: … runs/pending/<person>/judge.json` в выводе → выход судьи прошлого прогона не
записан в трекер: спроси, записать ли его (`append`, фаза 7) или выбросить; при `--no-ask`
прогон по человеку останавливается, в сводке путь файла. Такой строки нет → выход уже записан
(его sha256 есть в трекере), файл перезаписывается стабом без вопроса. Прочие строки `verify`
здесь не важны.

## Фаза 4. Коллекторы

По агенту на пачку, **все пачки человека одним сообщением параллельно** (при `--all` можно
собрать пачки нескольких людей в одно сообщение). Агент выбирается по таблице «Выбор агента»,
`model` из `config.models.collector`. Постановка — бриф коллектора из `references/orchestration.md`
с JSON-входом по таблице выше; `output_path` = свой стаб `<pending>/batch-NN.json`.

## Фаза 5. Проверка коллекторов

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" check-collector <pending>/batch-01.json <pending>/batch-02.json
```

Все файлы пачек человека одним вызовом. Однозначный ремонт цитат команда делает сама и пишет
в файл: номер хода, когда те же слова стоят ровно в одном другом ходе человека (или в команде и
выводе инструмента), и склейку кусков одной реплики человека без «…» (куски в исходном порядке,
от трёх слов и 15 знаков). Каждая правка — строка `check-collector: …` в `metadata.warnings`
пачки и в `repaired` вывода, со старым и новым ходом; из-за них коллектор не перезапускается,
в сводку человека идёт строка «цитаты исправлены» со списком `repaired` дословно.

`0` → к судье. `1` → в выводе кривые файлы (стаб не заполнен, поля оценки, схема, ось не
покрыта, цитата не сверилась с логом: текст агента или вставки под видом реплики человека,
те же слова в нескольких ходах человека, лог не найден): перезапуск этих коллекторов по разделу
«Перезапуск» в `references/orchestration.md`, руками JSON не правится. `2` → файлов нет:
проверь пути и стабы фазы 3.

После двух перезапусков проверка снова `1`, и в выводе только несверенные цитаты (лог найден)
→ прогон не останавливается, а отбрасывает эти записи:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" check-collector --drop-invalid <pending>/batch-01.json <pending>/batch-02.json
```

Каждая убранная запись — строка «отброшено: блок, сессия, ход, причина» в `metadata.warnings`
и в `dropped` вывода; ось, оставшаяся без наблюдений, уходит в `axes_unobserved` с причиной
`quote_unverified`. `0` → к судье, в сводку человека строка «наблюдения отброшены» со списком
`dropped` дословно. `1` → стоп по человеку, как при третьем отказе: схема, поля оценки, лог не
найден или у пачки не осталось ни одного наблюдения (пачка упала, файл не изменён).

## Фаза 6. Судья

Один на человека, после зелёного `check-collector`. Агент по таблице «Выбор агента», `model`
из `config.models.judge`, бриф судьи из `references/orchestration.md`. Судье подаются выходы
всех пачек в порядке `batch.index`, все логи прогона, `excluded_sessions[]` (из `short[]` со
статусом `transcript_too_short` и `skipped[]` со статусом `other_period`), `sessions_total`,
`card_slice` и `next_rec_number` (строкой задания «номер новой рекомендации начинать с
REC-<person>-<NNN>»). Сессии `other_period` в индексе не закрываются: `append` их не помечает, их
оценит прогон своего периода. После ответа `judge.json` не должен остаться стабом; остался или агент назвал
недостающее поле → поправить вход и перезапустить судью.

## Фаза 7. Запись прогона

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" append <pending>/judge.json --person <person> --period-confidence inferred
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" append <pending>/judge.json --person <person> --period-label <label> --period-confidence inferred
```

Первая строка — режим `run` или метки нет: `--period-label` не передаётся, метку выдаёт
`append`. Вторая — режимы `labels` и `dates` с меткой из `period_guess`.
Сразу после судьи, не откладывая. Вывод JSON: `run_id` (дальше только он), `period_label`
(итоговая метка периода, её называй в сводке), `logs_marked`, `logs_unmatched`,
`coverage{marked,expected}`, `warnings`. `1` → список нарушений схемы или
проверок (оценка без цитаты, уровень выше потолка гейта, запреты текста, рекомендации):
перезапуск судьи со списком, затем снова `append`. Номера рекомендаций `append` сам
перенумеровывает подряд со следующего свободного (в том числе после `retract`) и пишет об этом
строку «рекомендации перенумерованы: …» в `warnings`: это код `0`, судья не перезапускается,
в сводку строка идёт как предупреждение. `1` с текстом «уже есть прогон … с меткой» →
у человека живой прогон с этой меткой: повтор того же периода — `--replace <run_id>` из
сообщения, новый период — другая метка. `2` → вызов (карточка, метка, файл).
Переоценка уже записанного прогона — только через `--replace <run_id>`: сохраняются id и
правка ревьюера.

## Фаза 8. Пометки отсеянных

`append` помечает в индексе оценённые сессии и отсеянные, которые судья перечислил в
`session_scope`. Если `coverage.marked` меньше `coverage.expected` или `logs_unmatched` больше
нуля, догнать покрытие:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" mark-logs <run_id> --excluded <session_id_1>=not_batched <session_id_2>=not_batched
```

Все сессии — списком после одного `--excluded`; флаг можно повторять (то же у `--sessions`),
ссылки копятся, одна ссылка дважды → код `2`.

`mark-logs` добавляет пометки: ставит только сессии, которых у прогона ещё нет, уже
поставленные не трогает. `--force` нужен только для полной перепометки прогона (прежние
пометки откатываются и ставятся заново).

Причины исключения: `transcript_too_short`, `duplicate_export`, `not_batched`.

Сессия чужого периода (`other_period`) не исключается: запись индекса остаётся открытой для
прогона её периода, а такая причина в `--excluded` даёт код `2`. `1` → сессии не нашлись в
индексе, покрытие неполное или явная ссылка спорит с уже поставленной пометкой (перепометить
весь прогон: `--force`): сверить ссылки (id, префикс от 8 знаков, путь). Индекс руками не
правится.

## Фаза 9. Уровень

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" level <run_id>
```

Пишет `level_computed` (медиана оценённых осей, проверка результата дважды, потолок гейта).
Уровень служебный: адресату не показывается.

## Фаза 10. Текст ревью

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" render-review <pending>/judge.json --person <person> --run <run_id>
```

Пишет `<ws>/reviews/<person>/<run_id>.md`: служебный блок, отправляемый блок, досье. Вступление
(`feedback_parts.opening`) рендер берёт как есть, строку покрытия пишет судья. Статус: `self` →
`approved`; `team` и `course` при `reviewer_gate: true` → `draft`, до `approve`. `1` → нарушения
запретов текста (оценки, уровни, идентификаторы, сравнения, тире, обращение) или sha256 файла
не совпал с прогоном: файл не пишется; перезапуск судьи со списком, `append --replace <run_id>`,
`level`, снова `render-review`. В режимах team и course без `--no-ask` можно прогнать текст
через критика (бриф в `references/orchestration.md`) и показать его замечания ревьюеру.

## Фаза 11. Сверка

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sr.py" verify
```

`0` → каждый живой прогон закрыт: покрытие пометками, файл ревью, `level_computed`, сирот нет.
`1` → список проблем с готовой командой (`mark-logs`, `level`, `render-review`, `append`);
закрыть их и повторить `verify`. Прогон не называется сделанным, пока `verify` не зелёный.

## Фаза 12. Сводка

Пользователю, по человеку на строку, по шаблону из `references/orchestration.md`: период,
`run_id`, сколько сессий оценено и сколько исключено с причинами, пачек, статус текста
(`draft`/`approved`) и путь к файлу ревью, предупреждения судьи и команд, строки
«цитаты исправлены» и «наблюдения отброшены» из фазы 5 (дословно `repaired` и `dropped`),
«REC-… из неодобренного черновика <период> — вердикт отложен» и
«у <person> неодобренный черновик прошлого периода» из фазы 1. Оценок и уровня в
сводке нет (в режиме self — только при `show_scores`). По `--all` люди идут списком без
сравнений и рейтингов; кто без новых логов или остановлен, назван с причиной. Для `draft`
следующий шаг — прочитать текст и одобрить: `/sessionretro:review --approve <person>`.

Упёрся в ограничение плагина — протокол предложений: `${CLAUDE_PLUGIN_ROOT}/references/improvements-protocol.md`.

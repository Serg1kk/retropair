# Вопросы setup: формулировки, варианты, ответы

Справочник к `SKILL.md`: по каждому из 11 вопросов — формулировка, одна фраза «зачем», варианты
для AskUserQuestion и что из ответа кладётся в JSON для `setup-apply`. Правила диалога и порядок —
в `SKILL.md`; здесь только содержание.

Общее для всех вопросов:

- `header` — одно-два слова, не длиннее 12 знаков (указан у каждого вопроса).
- Вариантов 2–4; AskUserQuestion сам добавляет поле **Other** для свободного ввода. Всё, что нельзя
  выбрать из списка (id и имена людей, пути, даты, свой набор моделей), вводится через Other.
- Первый вариант — рекомендуемый на первом запуске или текущий на повторном, с пометкой
  `(Recommended)` в конце метки.
- Выбрал вариант, который просит ввод («впишу…»), но Other пустой → попроси данные одной репликой
  в формате из раздела вопроса; не придумывай значения.
- `{…}` в формулировке — подстановка из `setup-state --json` (`found.*` или `workspace.*`).

### Вопрос 1. Режим

`header`: «Режим». Ключ: `mode`.

**Вопрос:** «Кого разбираем: себя, команду или учебную группу?» На повторном: «Сейчас: {workspace.mode}. Сменить?»

**Зачем:** от режима зависят карточки людей, откуда берутся логи и кто одобряет текст перед отправкой.

Варианты, первый запуск:

1. «Себя (Recommended)» — режим self: один человек, карточка `me` создаётся сама, текст сразу готов.
2. «Команду» — режим team: тимлид разбирает участников, текст уходит только после одобрения.
3. «Учебную группу» — режим course: преподаватель разбирает учеников группы, тоже с одобрением.

На повторном запуске первым идёт текущий режим с `(Recommended)`, остальные два — следом. Смена
режима живого workspace — не ошибка: `setup-apply` предупредит советом, прошлые прогоны остаются.

```json
{"mode": "self"}
```

### Вопрос 2. Участники

`header`: «Люди». Ключ: `people`. **Не задаётся в self**: карточку `me` создаёт `setup-apply`.

**Вопрос:** «Кого добавить? Впишите в Other по строке на человека: `id; Имя; группа; логи`.»

**Зачем:** у каждого человека своя карточка и свои логи, текст пишется ему лично.

Варианты, первый запуск:

1. «Впишу список (Recommended)» — список в Other; если выбран без текста — попроси список одной репликой.
2. «Добавлю позже» — `people` не передаётся; потом повторный `/retropair:setup`.

Варианты, повторный запуск:

1. «Оставить как есть (Recommended)» — сейчас {число людей}: {id через запятую}; `people` не передаётся.
2. «Добавить людей» — новые строки в Other; существующие карточки `setup-apply` не перезаписывает.

Разбор строки `id; Имя; группа; логи`:

- `id` — латиница в нижнем регистре, цифры, дефис, начинается с буквы или цифры (`alex`, `maria-k`).
  Дали только имя — предложи id латиницей из имени и покажи его в итоговой таблице перед применением.
- `Имя` — как обращаться в тексте. Не дали — `name` не передаётся (будет равно id).
- `группа` — команда или учебная группа (`team-a`, `group-1`); пусто — первая группа workspace.
- `логи` — откуда брать логи человека: ссылка на git-репозиторий (`https://…`, `….git`) →
  `{"type": "git", "url": "…"}`; путь, оканчивающийся на `.specstory/history` →
  `{"type": "specstory", "path": "…"}`; любой другой путь → `{"type": "dir", "path": "…"}`;
  пусто или «нет» → без `sources`. Пути — абсолютные.

```json
{"people": [{"id": "alex", "name": "Alex", "group": "team-a", "sources": [{"type": "git", "url": "https://example.com/team/alex-logs.git"}]}, {"id": "maria", "name": "Maria", "group": "team-a"}]}
```

### Вопрос 3. Источники workspace

`header`: «Источники». Ключ: `sources` (источники без владельца; источники людей — в вопросе 2).

**Вопрос (self):** «Откуда брать логи? Нашёл {found.jsonl_files} сессий Claude Code этого проекта.» Папки
нет (`found.claude_projects_dir` null) — «Логов Claude Code этого проекта пока нет, папка появится
после первой сессии.»

**Зачем:** без источника сбору нечего читать, а ретро без логов не строится.

Варианты, self:

1. «Claude Code этого проекта (Recommended)» — `{"type": "claude-jsonl", "project": "auto"}`; если `found.specstory_dir` true, метка «Claude Code и SpecStory (Recommended)» и второй источник `{"type": "specstory", "path": ".specstory/history"}`.
2. «Только SpecStory» — `{"type": "specstory", "path": ".specstory/history"}`: для Codex, Cursor и других агентов.
3. «Своя папка с логами» — путь в Other → `{"type": "dir", "path": "…"}` (ручной экспорт `.md`, `.jsonl`).

Путь в Other, оканчивающийся на `.specstory/history`, → источник `specstory`, любой другой → `dir`.

**Вопрос (team, course):** «Общие источники без владельца нужны?»

Варианты, team и course:

1. «Только источники людей (Recommended)» — `"sources": []`: логи каждого берутся из его строки в вопросе 2; источник без владельца при двух и больше людях сбор не примет.
2. «Логи этого проекта, человек один» — только если в workspace ровно один человек: те же источники, что в self.

```json
{"sources": [{"type": "claude-jsonl", "project": "auto"}, {"type": "specstory", "path": ".specstory/history"}]}
```

### Вопрос 4. SpecStory

`header`: «SpecStory». Ключа ответа нет: вопрос только помогает поставить инструмент.
**Не задаётся**, если `found.specstory_version` — версия 2.6.0 или выше.

**Вопрос:** «SpecStory не найден (или версия ниже 2.6.0). Поставить?»

**Зачем:** SpecStory выгружает сессии Codex, Cursor и других агентов; логи Claude Code читаются и без него.

Варианты:

1. «Покажите, как поставить (Recommended)» — покажи команды ниже; запускает их пользователь сам.
2. «Без SpecStory» — ничего не ставим, сбор читает логи Claude Code напрямую.

Установка (macOS и Linux; под Windows SpecStory нет). Литерал `${CLAUDE_PLUGIN_ROOT}` в показанной
команде замени абсолютным путём корня плагина:

```bash
brew tap specstoryai/tap
brew install specstory
specstory version
mkdir -p ~/.specstory/cli
cp -n "${CLAUDE_PLUGIN_ROOT}/references/collector-instructions/specstory-config.toml" ~/.specstory/cli/config.toml
```

Конфиг `${CLAUDE_PLUGIN_ROOT}/references/collector-instructions/specstory-config.toml` выключает облако,
аналитику и проверку обновлений; `cp -n` не трогает уже лежащий конфиг. Версия ниже 2.6.0 —
`brew upgrade specstory`. `brew` ругается на Command Line Tools — готовый бинарь, шаги в
`${CLAUDE_PLUGIN_ROOT}/references/collector-instructions/cursor.md`, раздел «Шаг 1». В Claude Code
команды удобно запустить прямо в чате с префиксом `!`.

### Вопрос 5. Хук

`header`: «Хук». Ключ: `hook`.

**Вопрос:** «Собирать логи сами в конце каждой сессии Claude Code?» На повторном: «Сейчас: {включён|выключен}.»

**Зачем:** хук SessionEnd запускает сбор в фоне, и к ретро логи уже на месте, без ручной команды.

Варианты:

1. «Автоматически (Recommended)» — `"hook": true`: хук SessionEnd, фоном, вывод в `.retropair/collect.log`.
2. «Вручную» — `"hook": false`: сбор командой `/retropair:collect`, когда нужно.

```json
{"hook": true}
```

### Вопрос 6. Модели и effort

`header`: «Модели». Ключ: `models` (можно одну роль).

**Вопрос:** «Какой набор моделей для агентов? Коллектор читает логи пачками, судья ставит оценки и
пишет текст, критик проверяет текст.»

**Зачем:** цена прогона и качество оценки зависят от моделей: судья решает, коллектор готовит факты.

Варианты, первый запуск:

1. «Сбалансировано (Recommended)» — коллектор sonnet/medium, судья opus/high, критик sonnet/medium: сильная модель там, где решается оценка; средняя цена.
2. «Экономно» — коллектор haiku/low, судья sonnet/medium, критик haiku/low: в разы дешевле, но коллектор пропускает тонкие места и цитат у судьи меньше.
3. «Максимум» — коллектор opus/high, судья opus/max, критик opus/medium: лучшее качество, самая высокая цена и самый долгий прогон.
4. «Свой» — впишите в Other `роль=модель/effort` через запятую, например `judge=opus/max`; модели `sonnet`, `opus`, `haiku`, `inherit`, effort `low`, `medium`, `high`, `max`.

На повторном запуске первым идёт «Как сейчас (Recommended)» с текущими значениями, дальше три
пресета, кроме совпавшего с текущим; «Свой» — через Other.

Сбалансировано:

```json
{"models": {"collector": {"model": "sonnet", "effort": "medium"}, "judge": {"model": "opus", "effort": "high"}, "critic": {"model": "sonnet", "effort": "medium"}}}
```

Экономно:

```json
{"models": {"collector": {"model": "haiku", "effort": "low"}, "judge": {"model": "sonnet", "effort": "medium"}, "critic": {"model": "haiku", "effort": "low"}}}
```

Максимум:

```json
{"models": {"collector": {"model": "opus", "effort": "high"}, "judge": {"model": "opus", "effort": "max"}, "critic": {"model": "opus", "effort": "medium"}}}
```

Свой (`judge=opus/max`):

```json
{"models": {"judge": {"model": "opus", "effort": "max"}}}
```

`setup-apply` пишет модели в конфиг и переписывает проектных агентов `.claude/agents/retropair-*.md`.
Агент, у которого пользователь правил тело, не трогается: придёт совет с командой `agents write --force`.

### Вопрос 7. Баллы в личном отчёте

`header`: «Баллы». Ключ: `show_scores`.

**Вопрос:** «Показывать баллы по осям и уровень в личных отчётах?»

**Зачем:** личный отчёт — та же карточка, что у ревьюера, без служебного; баллы на графиках
помогают увидеть, где сдвинулось. Текст ревью баллов не содержит в любом случае.

Варианты:

1. «Да, баллы и уровень (Recommended)» — `"show_scores": true`; в team и course баллы увидит каждый, кому отдадут личный отчёт.
2. «Нет, только динамика» — `"show_scores": false`: вместо баллов переходы ↑ лучше, → ровно, ↓ ниже, ◇ нет данных.

Вид можно поменять при каждой сборке отчётов (`report --scores` / `--trend`) и для одного
человека (`feedback.show_scores` в его карточке).

```json
{"show_scores": true}
```

### Вопрос 8. Периоды

`header`: «Периоды». Ключ: `period`.

**Вопрос:** «Как делить работу на периоды для ретро?»

**Зачем:** период — единица сравнения: динамика и рекомендации считаются от периода к периоду.

Варианты:

1. «По дате запуска (Recommended)» — `{"mode": "run"}`: каждый прогон — свой период с меткой по дате.
2. «Окна дат» — `{"mode": "dates", "windows": […]}`: окна в Other по строке `метка: ГГГГ-ММ-ДД — ГГГГ-ММ-ДД` (пустая граница открыта; `from` не позже `to`, метки не повторяются, иначе `setup-apply` вернёт код 2 с номером окна — переспросите).
3. «Без меток» — `{"mode": "labels"}`: в 0.2 скилл `review` метку не спрашивает, прогоны пишутся без метки периода. Своё имя периода — через «Окна дат».

```json
{"period": {"mode": "dates", "windows": [{"label": "sprint-1", "from": "2026-09-01", "to": "2026-09-14"}, {"label": "sprint-2", "from": "2026-09-15", "to": null}]}}
```

### Вопрос 9. Шаблон текста

`header`: «Шаблон». Ключ: `template`.

**Вопрос:** «Каким шаблоном оформлять текст человеку?»

**Зачем:** шаблон задаёт только оформление текста: порядок частей, приветствие, подпись.

Варианты:

1. «Шаблон плагина (Recommended)» — `"template": "default"`.
2. «Своя копия шаблона» — `"template": "workspace"`: `setup-apply` положит копию в `.retropair/templates/feedback.md`, если её там нет, и пропишет её в `feedback.template` файла `people/_default.yaml`; правьте копию.

Other — имя своего файла в `.retropair/templates/` без папок и `..` (`"template": "short.md"`); файл уже должен лежать там, иначе код 2. Карточки со своим `feedback.template` выбор не меняет — `setup-apply` перечислит их советом.

```json
{"template": "workspace"}
```

### Вопрос 10. Срок хранения логов Claude Code

`header`: «Хранение». Ключ: `cleanup_period_days` (объект `{"value": …, "write": …}`).
**Не задаётся**, если `found.cleanup_period_days` уже 90 или больше.

**Вопрос:** «Claude Code удаляет логи сессий старше {found.cleanup_period_days или «30 (по умолчанию)»}
дней. Поставить 90 в `~/.claude/settings.json`?»

**Зачем:** логи, удалённые до ретро, не собрать: период останется без данных.

Варианты:

1. «Да, поставить 90 (Recommended)» — `"write": true`: `setup-apply` допишет ключ, остальные настройки файла сохранятся.
2. «Нет, только совет» — `"write": false`: файл не трогается, в выводе будет совет с текущим значением.

Other с числом дней N и согласием записать — `{"value": N, "write": true}`. `"write": true` — только
после явного «да»; любой другой ответ — `"write": false`.

Да:

```json
{"cleanup_period_days": {"value": 90, "write": true}}
```

Нет:

```json
{"cleanup_period_days": {"value": 90, "write": false}}
```

### Вопрос 11. .gitignore

`header`: «gitignore». Ключ: `gitignore`.

**Вопрос:** «Дописать в `.gitignore` проекта логи, черновики и отчёты RetroPair?»

**Зачем:** в логах ваш код и переписка, а черновики и отчёты — личные тексты; им не место в общем репозитории.

Варианты:

1. «Да, дописать (Recommended)» — `"gitignore": true`: добавятся недостающие строки `.retropair/logs/`, `.retropair/runs/pending/`, `.retropair/reports/`.
2. «Нет» — ключ не передаётся, `.gitignore` не трогается.

```json
{"gitignore": true}
```

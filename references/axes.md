# Оси оценки процесса работы с кодинг-агентом

axes_version: v3

> Референс агентов `log-judge` и `log-collector`. Источники: публичные источники и практика
> работы с кодинг-агентами. Правки этого файла обязаны сопровождаться бампом `prompt_version`
> агента.

## Как читать этот файл

Восемь осей, шкала 0–4 на каждой либо `insufficient_evidence`. Балл ставится **только** под
дословную цитату с номером хода. Ноль это положительно установленное плохое поведение;
отсутствие сигнала это `insufficient_evidence`, и эти два состояния путать нельзя.

**Что оценивается:** ведение агента человеком. **Что не оценивается:** качество кода,
архитектура, полнота решения, красота формулировок, длина реплик, скорость.

### Общие правила, действующие на все оси

1. **Отсутствие сигнала ≠ провал.** Человек мог проверить в соседнем терминале, прочитать
   дифф глазами, обсудить голосом. В транскрипт это не попадает.
2. **Короткая реплика ≠ пассивность.** Опытный человек экономит на словах; неноситель языка
   пишет короче; голосовой ввод даёт другой стиль. Длина в оценку не входит ни прямо, ни
   косвенно.
3. **Асимметрия инструментов.** Claude Code и Codex CLI дают полный трейс команд и вывода,
   Cursor даёт диалог без терминала, Copilot почти не даёт трейса. Признаки, живущие в **тексте
   человека**, наблюдаемы везде и несут основной вес. Признаки, живущие в **трейсе
   инструментов**, подтверждают, но их отсутствие ничего не доказывает.
4. **Уверенный тон человека не повышает балл.** «Я всё посмотрел, ок» это утверждение, а не
   доказательство. Засчитывается конкретика: имя файла, кейса, строки, числа.
5. **Одна реплика может кормить две оси.** Дублирование лучше потери сигнала, но границы ниже
   соблюдать обязательно, иначе одно действие двигает два балла и график покажет связь,
   которой нет.
6. **Балл ставится по наблюдаемым под-критериям, ненаблюдаемые вниз не тянут.** Под-критерий,
   для которого в логе нет ни положительного, ни отрицательного материала, **выпадает из
   знаменателя**, а не считается проваленным. Ось оценивается по тому, что видно.
   - **Ненаблюдаемых больше половины → вся ось `insufficient_evidence`**, даже если по
     оставшимся виден приличный сигнал. Балл, стоящий на одном под-критерии из пяти, это
     не оценка, а угадывание.
   - Что именно выпало и почему, называется в `note` оси: «ветки и изоляция в логе не
     наблюдаемы, балл по точкам возврата и размеру шага».
   - Материал бывает не только в логе: под-критерий, невозможный на этом проекте в принципе
     (тестов нет вовсе, версионирования нет вовсе), тоже выпадает из знаменателя.
   **Пример:** по `reversibility` видны коммиты по границам кусков, но не видно ни веток, ни
   фиксации до прогона. Поставить оси 2 из-за того, что два под-критерия из пяти просто не
   наблюдались, это занижение, а не строгость.

### Границы между конкурирующими осями (соблюдать дословно)

| Пара | Граница |
|---|---|
| `verification` / `ownership` | Отклонение по **добытому свидетельству** (тесты красные, метода нет в библиотеке) это `verification`. Отклонение по **рассуждению без свидетельства** («это ломает границу транзакции») это `ownership` |
| `self_correction` / `trust_calibration` | Решение **после** случившегося провала это `self_correction`. Решение, принятое **до** провала или вовсе без него, по оценке риска («это авторизация, тут я сам») это `trust_calibration` |
| `decomposition` / `context_engineering` | «Почему работа разрезана здесь» (единица работы, размер куска) это `decomposition`. «Что при разрезе унесено, а что осознанно отброшено» это `context_engineering` |
| `task_framing` / `decomposition` | Содержание постановки (что считается сделанным, какие ограничения) это `task_framing`. Размер и порядок отданного за один раз это `decomposition` |
| `task_framing` / `verification` | Критерий приёмки, записанный в промпт **до** генерации, это `task_framing`. Факт прогона проверки **после** генерации это `verification` |
| `reversibility` / `verification` | «Узнает ли человек, что откат нужен» это `verification`. «Что будет стоить откат» это `reversibility` |

## 1. `verification` — Проверка результата

_Верификация и недоверие к выводу._

**Вес: максимальный.** Меряет, делает ли человек проверку частью задачи и принимает ли
результат только против наблюдаемого доказательства.

**Под-критерии:** критерий готовности задан до работы · граничные случаи названы человеком,
а не сгенерированы · проверка реально запущена · вывод прочитан и расхождение отработано
предметно · недоверие к самоотчёту агента · судья вне рук исполнителя (тесты не правятся ради
зелёного) · проверка внешних фактов (существует ли пакет, метод, версия) · соразмерность
объёма проверки цене ошибки · проверка глазами пользователя поверх зелёных тестов · находка
закрепляется тестом · **просмотр всего диффа, а не только запрошенного** (агент штатно трогает
лок-файлы, конфиги CI, соседние тесты).

**Сильные маркеры:** «и прогони тесты», «готово, когда», перечисление кейсов с ожиданиями
(`"" → false`, «регистр не важен», «истёкший»), цитата из вывода в реплике человека, имя
упавшего теста, «покажи вывод, а не пересказ», «тесты не трогай, чини код», «такого метода
нет», `pytest`/`npm test`/`npm run build`/`curl`/`tsc --noEmit` с последующей реакцией.

**Антисигналы:** «выглядит правильно», «ок, дальше» сразу после крупного диффа; согласие после
«все тесты прошли» без блока вывода; цикл «вставил ошибку → почини» без единой содержательной
реплики.

**Якоря.** **0** — приёмка по виду: есть содержательные изменения и есть положительный признак
приёмки без проверки. **1** — проверка только после аварии, запускает её сбой, а не замысел.
**2** — проверки регулярны, но состав и полноту определяет агент: «покрой тестами» → «14 passed»
→ «отлично». **3** — проверка заказана вместе с задачей, вывод читается по содержанию,
расхождение отрабатывается предметно; объём одинаков для любого изменения. **4** — критерий
и граничные случаи сформулированы до кода и часть их из знания домена; объём явно разный на
разных изменениях; человек ловит попытку подогнать **проверку** под зелёный результат
(правленый ассёрт, `skip`, зашитое под конкретный вход ожидание, ослабленный сценарий прогона);
находка закрепляется **воспроизводимой проверкой** (тест, скрипт прогона, записанный сценарий
вызовов, кейс в наборе).

⚠️ **Проверка это не обязательно тест.** На проектах без тестового фреймворка (инфраструктура,
интеграции, MCP-серверы, цепочки n8n, скрипты) вся проверка идёт прогонами и глазами, и это
полноценная верификация: вызов инструмента через MCP Inspector, дёрганье эндпоинта, запуск
сценария и просмотр строки в базе, ручной прогон цепочки с разбором выхода. Под-критерии,
сформулированные через тест, читаются по сути («судья вне рук исполнителя» = проверка не
подгоняется под желаемый результат), а при отсутствии материала **выпадают из знаменателя**
по общему правилу 6. Потолок 3 «потому что тестов нет» это дефект оценки.

⚠️ **`verification_commands: 0` из механических метрик не означает «не проверял».** Детектор
ищет `pytest` / `npm test` / `curl` и не видит проверку через инструменты MCP, Inspector и
веб-интерфейс. Число тут опора, а не вердикт: смотри текст.

**`insufficient_evidence`:** есть следы проверки вне лога («у меня падает на третьем
пользователе», «прогнал у себя»); инструмент не пишет трейс; лог обрезан; изменений не было
вовсе; изменение тривиально; проверка вынесена в CI; сессия слишком коротка.
**Ноль требует положительного доказательства приёмки без проверки. «Ни одного запуска в логе»
основанием не является.**

## 2. `task_framing` — Постановка задачи

Меряет, что человек положил в промпт **до** запуска агента и **в какой момент** положил.

### 🔴 Происхождение промпта не оценивается

**Откуда взят промпт, значения не имеет.** Скопировал из учебных материалов, нашёл в интернете,
сгенерировал моделью, написал сам — всё это одно и то же. Оценивается то, что человек
**применил хороший промпт в работе с агентом**, и это засчитывается как есть.

- Сверять текст с исходными материалами не надо, отдельного разбора «своё против
  скопированного» быть не должно.

**Пять элементов (под-критерии).** Проверяются по наличию смысла в тексте, а не по заголовкам:

| Элемент | Что ищем | Отсутствие даёт |
|---|---|---|
| Контекст | Симптом и причина, факт, которого агент не мог вывести из репозитория | Агент додумывает мотив и решает не ту задачу |
| Ссылки | Путь, имя функции, `@`-упоминание, ссылка по концепции (вес 0.5) | Агент изобретает свой стиль вместо принятого |
| Задача | Ровно одно действие | Части упущены, дифф нечитаемый |
| Формат | Форма результата, когда она выбираема | Часто отсутствует законно; дефект, только если позже возник спор о форме |
| Ограничения | **Адресный** запрет: файл, слой, зависимость, объём | Подарки в довесок и реплика-уборка |

Адресный запрет («не трогай `prisma/schema.prisma`», «без новых зависимостей») засчитывается;
вежливый («не сломай ничего», «сделай аккуратно», «постарайся не менять лишнего») нет.

**Дополнительно:** план до кода (запрошен / формально принят «ок» / отревьюен по пунктам /
осознанно пропущен на мелочи) · уровень конкретности под то, что человек реально знает
(исследование / направление / спецификация) · интервью-паттерн («задай мне вопросы») с
**содержательными** ответами · разведка до первой правки · доопределение по ходу в ответ на
вопрос агента.

**Момент появления элемента меняет вес:** в постановочном промпте (полный) → добавлен позже по
своей инициативе до уборки (0.75) → в ответ на вопрос агента (0.5) → **после** реплики-уборки
(0.25) → отсутствует (0). Реплика-уборка («убери», «откати», «я не просил», «зачем ты это
добавил») это разделитель: после неё цена отсутствующего элемента уже оплачена руками.
**Рамка, собранная целиком задним числом, выше 3 не поднимается.**

**Якоря.** **0** — назван объект и действие, больше ничего, дальше «не то, переделай» без
уточнений. **1** — только задача как действие; ограничения появляются исключительно после
уборки. **2** — два-три элемента, рамка собирается по ходу диалога. **3** — четыре элемента из
пяти релевантных стоят в постановочном промпте, на многофайловой работе план запрошен и бегло
отревьюен. **4** — все релевантные элементы сразу, контекст несёт факт, которого нет в
репозитории, ограничения адресные, критерий проверяемый, реплик-уборок нет.

**`insufficient_evidence`:** лог начинается не с начала («да, давай так» без предшествующего);
всё содержимое это микро-правки в один файл; постановка вынесена во вложение, которого нет
(«делай по spec.md»); работа без текстовых промптов; лог короче трёх обменов.
⚠️ Если элементы рамки живут в файле правил проекта, а поведение агента это выдаёт, элемент
помечается `externalized` и **из знаменателя исключается**: вынести постоянные ограничения в
файл правил это правильное поведение, а не пробел.

## 3. `ownership` — Решения за собой

_Самостоятельность и способность объяснить свой дифф._

Меряет, остался ли человек автором решений после того, как код начал писать агент.
**Это не частота вмешательств:** короткое подтверждение после самостоятельно заданной рамки
это владение, а бесконечные правки имён при молча принятой схеме данных это ложное владение.

**Под-критерии:** контакт с диффом (ссылка на конкретное место) · отклонение с причиной ·
уточняющий вопрос про механику, а не про статус · требование объяснить дифф · ручное
вмешательство · возражение против архитектурного хода · реакция на предупреждение агента ·
отсечение лишнего · проверка рапорта («всё готово» это утверждение, не факт) · названный
компромисс · возврат к своей же рамке · признание непонимания **с последующим разбором**.

**Осознанное делегирование против пассажира** различается не по реплике, а по контексту:
была ли до этого задана рамка; делегируется мелкое и обратимое или всё подряд; есть ли
асимметрия внимания; есть ли хотя бы один аргументированный отказ за сессию; возвращается ли
человек к результату; назван ли стейкс («это прототип, выкинем»).

**Якоря.** **0** — вывод попадает в кодовую базу без контакта: универсальные подтверждения,
статусные вопросы, ноль отказов. **1** — реагирует на боль, но не на решения: «опять та же
ошибка, почини». **2** — точечные возражения без рамки, причины через раз, крупные ходы
проходят мимо. **3** — отказы аргументированы, вопросы про механику заданы, лишнее срезано, на
предупреждения отвечает по существу. **4** — рамка задана до старта, различение делегируемого
и удерживаемого явное, расхождение между рапортом и фактом ловится.

**`insufficient_evidence`:** сессия короткая по решениям; сессия целиком про понимание кода без
изменений; лог обрезан; работа шла вне транскрипта; авторство строк в диффе не размечено.

## 4. `self_correction` — Смена подхода после неудачи

_Итеративность и самокоррекция._

Меряет, что человек делает **после того, как вывод не подошёл**. Не количество итераций:
итеративность это нормальный режим работы. Плохо не то, что итераций много, а то, что они не
несут нового.

**Три несущих вещи:** прирост информации между попытками · смена рычага при повторной неудаче
(промпт → тест или фикстура → правило в файле → откат → рестарт) · наличие стоп-правила.

**Петля против продуктивной итерации:**

| Признак | Продуктивная | Петля |
|---|---|---|
| Содержание следующей реплики | Новый факт: ошибка, вход, ограничение | Та же мысль другими словами |
| Адресация | Файл, строка, кейс | «не работает», «исправь» |
| Объём шага | Сужается | Не меняется или расширяется («заодно») |
| Состояние базы | Неудачная правка откачена | Правки поверх неоткаченных |
| Траектория ошибки | Ошибка меняется | Та же либо ходит по кругу |

**Сильные положительные маркеры:** «стоп, не правь пока, дай гипотезы», «/clear», «начнём
заново», «собери summary файлом», прерывание агента на ходу, «добавь тест на этот случай»,
«запиши это в правила», сужение до минимального репро.
**Отрицательные:** третье подряд «исправь» без указания на что; «не работает» короткой репликой
без вывода; дословный повтор предыдущего промпта; реверс-пары («верни как было») в полировке;
5+ вкусовых правок одного экрана без названного критерия готовности.

**Фрустрация (капслок, «!!!», мат) сама по себе балл не понижает.** Она только повышает
уверенность в уже найденной петле.

**Якоря.** **0** — реакция одна и та же независимо от номера провала, новых фактов нет, ни
одного отката. **1** — рычаг ровно один, правка промпта; серия 4+, стоп-правила нет. **2** —
умеет указать точно, но на сложном дефекте порога нет, причина не запрашивалась ни разу.
**3** — после второй неудачи меняется уровень вмешательства, есть осознанный сброс, ограничение
хотя бы раз ушло в файл правил. **4** — то же плюс перенос знания через сброс и упреждение:
прерывает на первых признаках, полировка ограничена критерием, названным заранее.

**`insufficient_evidence`:** в логе не было ни одной неудачи; лог обрезан; работа велась вне
транскрипта.

## 5. `context_engineering` — Работа с контекстом

_Контекст-инжиниринг и управление окном._

Меряет работу с тем, **что видит модель**: чем человек заполняет окно, что выносит наружу
в файлы, что делает, когда окно распухает.

**Три слоя.** (1) Постоянный контекст: файл правил агента. (2) Оперативный: чем кормится окно
под задачу. (3) Управление окном во времени: разрез по фазам, компакты, реакция на
авто-компакт.

**Файл правил: качество не оценивается.** Объём, конкретность, число лозунгов, живость по
истории коммитов — это оценка артефакта вне лога, а не разбор логов. Здесь остаётся
единственный вопрос, на который отвечает сам лог: **опирался ли агент на правила в этой
сессии.** Сильнейший тест: агент выполнил проектную команду, которой человек
в этой сессии не называл (свериться можно по `repo_path`). Одного совпадения достаточно. Слабее, но годится: агент сослался на
правила; человеку не пришлось пересказывать конвенции руками в каждом промпте.

| В логе | Вывод |
|---|---|
| Человек пересказывает конвенции руками в каждом промпте | Опоры нет, вывод уверенный |
| Есть сигнал опоры | Закрыто положительно |
| Сигналов нет ни в ту, ни в другую сторону | `insufficient_evidence`, **снижать нельзя** |

⚠️ Заглянуть в репозиторий, чтобы понять, о каком файле или команде речь, можно. Но лог это
состояние на момент сессии, а репозиторий — на сегодня: **расхождение между ними находкой
не является.**

**Чтение `context_report` (если есть).** Ручной компакт с инструкцией и разрез по фазам это
плюс; авто-компакт посреди задачи это минус, а авто-компакт **без перебрифовки после него**
ограничивает балл сверху; два и более авто-компакта в одной сессии ограничивают жёстче; пик
выше 90% при финале ≈ пик и без компактов это сильный минус. Окно миллионного размера считать
по абсолютной величине: выше ~200K токенов внутри одной задачи это уже зона деградации.
**Отсутствие `context_report` (Cursor и прочие) балл не снижает: числовые правила просто не
применяются.**

**Якоря.** **0** — контекст не управляется: конвенции пересказываются каждую сессию, контекст
задачи подаётся пересказом при доступном файле, «изучи весь репозиторий», темы смешаны.
**1** — элементы есть, системы нет; конвенции всплывают в промптах вперемешку с задачей.
**2** — базовая гигиена: файлы подкладываются адресно, трейсы вставляются целиком, авто-компакт
замечен и отработан. **3** — агент опирается на правила без напоминаний, границы фаз обозначены
явно. **4** — плюс контекст ведётся как артефакт: итог сессии оставляется файлом перед сбросом,
компакт ручной с инструкцией, тяжёлое чтение уходит в отдельный прогон.

**`insufficient_evidence`:** по слоям отдельно, а не по оси целиком (опоры на правила в логе
не видно → слой 1; `context_report` нет → числовая часть слоя 3; одна короткая сессия → разрез
не проверялся).
Отсутствие следов `/clear` это `insufficient_evidence` по разрезу, а не «человек не резал».

## 6. `decomposition` — Разбиение работы

_Декомпозиция и оркестрация._

Меряет, как человек нарезает работу и куда кладёт каждый кусок: размер захода, места разрезов,
выбор исполнителя (тот же чат, чистый чат, субагент, отдельный терминал).

**Под-критерии:** атомарность промпта · объём захода между двумя точками проверки · границы по
связности · план до кода · такт цикла (проверка и фиксация между задачами) · чистый контекст
на новую задачу · делегирование разведки с возвратом выжимки · границы исследования ·
соразмерность усилия (глубина рассуждений под тип куска) · точка сборки результатов.

**Две крайности лечатся противоположно, поэтому различать обязательно.** Мегазадача: список
целей одним промптом, правки в 10+ файлах, ни одной проверки. Микроменеджмент: диктант способа
(«открой файл X, поменяй функцию Y») без критерия готовности, агент лепит заглушки, не видя
соседнего кода. **Различитель:** здоровая атомарность сужает **предмет** и оставляет агенту
**способ**; микроменеджмент сужает способ и часто не называет критерий. Второй различитель:
можно ли принять и откатить два соседних захода независимо.

**Якоря.** **0** — работа отдана одним куском, границ нет, часть заявленного не сделана и
обнаружено случайно. **1** — деление случайное и не выдержанное («заодно»), либо зеркальный
диктант. **2** — разбито по фичам внятного размера, но такта нет: между задачами не проверяется
и не фиксируется. **3** — атомарные задачи с рабочим тактом, план на неочевидном запрошен и
утверждён с правками, разведка ограничена папкой и вопросом. **4** — плюс осознанная
оркестрация под форму работы: состав выясняется отдельной фазой, независимые куски идут в своих
контекстах, результаты сходятся в один артефакт, глубина рассуждений подобрана.

**`insufficient_evidence`:** одна мелкая задача, резать было нечего; лог обрезан; сессия
исследовательская.

## 7. `trust_calibration` — Мера доверия агенту

_Калибровка доверия и выбор инструмента._

Меряет, **меняется ли доверие вместе с ценой ошибки**, и подбирается ли инструмент под задачу.
**Шкала двусторонняя:** и слепое доверие, и недоверие-паранойя одинаково плохи. Хорошо
соответствие доверия риску.

**Под-критерии:** дифференциация по цене ошибки · осознанная остановка доверия с названной
причиной · выбор модели и уровня рассуждения под задачу · разная свобода в постановке в
зависимости от цены неверного выбора · обращение с необратимыми операциями (миграции, удаление,
force push, прод-данные) · настройка среды до начала работы (ветка, контейнер, тестовая база) ·
режим разрешений под среду · проверка внешних фактов в источнике, а не переспрашиванием той же
модели · отношение к отчёту агента о собственной работе · реакция на предупреждение · пересмотр
доверия по ходу с названной причиной · **названное основание не проверять** («обратимо, не
смотрю», «покрыто тестами») это самый сильный признак рамки.

⚠️ **Расхождение декларации и поведения оценивается по поведению.** «Я такому не верю» и через
две реплики «да, применяй» на изменение схемы это не высокий балл.
⚠️ **Скрытая паранойя:** проверяет всё одинаково подробно и потому проверяет плохо, при этом
необратимая операция в том же логе проходит мимо.
⚠️ Смена модели из-за лимитов или цены это управление ресурсом, а не калибровка: засчитывается,
только если названо свойство задачи.

**Якоря.** **0** — доверие не различается: на миграцию и на переименование одинаковое «ок,
давай». Сюда же зеркальный край: не делегирует ничего. **1** — различие декларируется, но не
выполняется, либо торможение случается там, где дёшево. **2** — один устойчивый рабочий рубеж,
и он соблюдается. **3** — доверие различается по классам задач, основания названы, внешние
факты проверяются в источнике. **4** — плюс среда ограничивается заранее под радиус поражения,
доверие пересматривается по ходу с названной причиной и классом задач, есть явные места
осознанного непроверения.

**`insufficient_evidence`:** в логе нет операций с разной ценой ошибки; инструмент один и
переключений не предполагает; сессия однородная.

## 8. `reversibility` — Возможность отката

_Обратимость и цена отката._

Меряет, насколько дёшево человеку отменить неудачный ход агента: размер шага между точками
возврата относительно радиуса поражения того, что агент делает в этом прогоне.

**Под-критерии:** точка возврата перед прогоном · размер шага (один прогон = один откатываемый
шаг) · изоляция под риск (ветка, worktree, копия) · откат как штатный ход (плохой по существу
результат выбрасывается целиком, а не чинится поверх) · чистота дерева на входе.

**Маркеры положительные:** `git commit`, `git switch -c`, `git worktree add`, `git stash`,
`git restore`, `git revert`, `git diff` в теле лога; «сначала закоммить», «зафиксируй рабочее
состояние», «откатись», «выброси и переделай с нуля»; встроенные чекпоинты инструмента.
**Отрицательные:** `git add -A` в грязном дереве; единственный коммит в конце сессии
с сообщением «работа за день»; `git push --force` в общую ветку; «уже не помню, что тут было
до агента»; «давай просто починим поверх» после третьей неудачи.

**Якоря.** **0** — точек возврата нет, чинит поверх, потому что вернуться некуда; либо агент
запущен поверх грязного дерева. **1** — версионирование не связано с работой агента: один
коммит в конце. **2** — фиксация перед крупными прогонами есть, но шаг крупный, отдельную фичу
не вынуть. **3** — состояние зафиксировано до прогона, шаг равен единице работы, рискованное
идёт в ветке, есть хотя бы один осознанный выброс результата. **4** — плюс шаг подобран под
радиус поражения конкретного прогона, решение о точке возврата принимается до запуска и
проговаривается.

⚠️ **Не считать высоким баллом:** коммит-спам (точек много, рабочих ни одной), заведённая и
брошенная ветка, `git add -A` в грязном дереве, откат-паника без понимания потерянного.

**`insufficient_evidence`:** правки были, а версионирования в логе не видно — это
`insufficient_evidence`, **а не ноль**: человек мог коммитить в соседнем терминале. В разборе
ставится пометка «версионирование за пределами лога». Ноль ставится только при положительном
признаке: чинил поверх, потому что возвращаться некуда; работал по грязному дереву.

⚠️ **Ветки, worktree и изоляция на одиночном небольшом проекте часто не наблюдаемы вовсе**, и
на многих задачах они там просто не нужны. По общему правилу 6 такие под-критерии выпадают из
знаменателя: балл ставится по тому, что видно (точки возврата, размер шага, откат как штатный
ход), а не удерживается на 2 из-за неувиденного.

## Gating: потолок итогового уровня

Гейт **не обнуляет** оценку, он ограничивает верх итогового уровня. Строится на **присутствии**
маркеров, молчание в логе гейт не запускает никогда.

| ID | Триггер | Дополнительное условие |
|---|---|---|
| G1 | Слепое принятие крупного объёма: единственная реплика «ок / да / lgtm / go ahead» | Изменение затрагивает несколько файлов, схему, зависимости или контракт, **и** за сессию нет ни одного маркера владения |
| G2 | «На твоё усмотрение» на вопрос выбора | Вопрос требует знания домена или продуктового намерения, человек единственный источник ответа, основание не названо |
| G3 | Глухота к предупреждению | Агент сказал «это сломает X» / «потребуется миграция» / «есть риск потери данных», человек в следующей реплике на это не отвечает |
| G4 | Приёмка рапорта без проверки | После «всё готово» переход к следующей задаче без запроса подтверждения, запуска или сверки |
| G5 | Заявленное непонимание без устранения | «не понял, но ок», «лишь бы работало», «просто убери ошибку» — реплика терминальная, разбора после неё нет |
| G6 | Нулевая позиция на длинной сессии | Много ходов, крупный суммарный дифф, ноль отказов, уточнений, правок руками и срезов лишнего |

**Потолок:** один сработавший триггер ограничивает итоговый уровень серединой (`competent`),
два и более нижней третью (`developing`).

**Где гейт НЕ срабатывает:** короткое подтверждение после самостоятельно заданной рамки ·
«на твоё усмотрение» по безразличному вопросу (имя переменной, порядок полей) · снятие вопроса
с названным основанием («это одноразовый скрипт») · малый дифф · явно низкий стейкс (песочница,
разведка, прототип) · контроль инструментом вместо чтения (прогнал тесты, натравил второго
агента на ревью) · отложенная реакция (через два хода человек показывает, что читал) ·
прерывание агента на ходу.

## Итоговый уровень

`passenger` · `naive` · `competent` · `confident_operator` · `orchestrator`, плюс `developing`
как потолок при сработавшем гейте и `insufficient`, когда данных мало.

**Уровень считает скрипт**, а не судья: медиана оценённых осей, в которой `verification`
учитывается дважды (вес максимальный); пороги 3.5 / 2.75 / 2.0 / 1.0: `orchestrator` ≥ 3.5 ·
`confident_operator` ≥ 2.75 · `competent` ≥ 2.0 · `naive` ≥ 1.0 · ниже — `passenger`. Меньше
трёх оценённых осей — мало данных (`insufficient`). Гейт: 1 сработавший триггер — не выше
`competent`, 2 и больше — `developing`. Оси с `insufficient_evidence` в медиану не входят.

Судья ставит свой уровень (`level_judge`) только для сверки со скриптом; расхождение идёт
строкой в отчёт ревьюеру. **Уровни и баллы в текст адресату не попадают никогда**; показ
баллов в режиме самопроверки включается флагом конфигурации на стороне отчёта, не текстом
судьи.

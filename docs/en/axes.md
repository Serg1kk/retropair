# The eight axes: what sessionretro looks for in the logs

sessionretro looks at **how a person leads a coding agent**: how they frame the task, verify the
result, keep the decisions in their own hands and slice the work. The assessment runs on eight
axes.

What is **never assessed**: code quality, architecture, completeness of the solution, polish of the
wording, message length and speed. A short message is not passivity: an experienced person saves
words, and voice input produces a different style. A confident tone adds nothing either: "I've
looked at everything" is a claim; what counts is the specifics (a file, a case, a line, a number).

Every conclusion stands on a verbatim quote from the log. No quote, no conclusion.

## The eight axes

### Verifying results

The most important axis: it counts twice in the overall level. We look at whether the person makes
verification part of the task and accepts the result on evidence rather than on looks.

- **Counts:** the definition of done is named before the work; edge cases are thought up by the
  person; a check is actually run and its output read; the person does not take the agent's
  report on trust; the whole diff is reviewed, not only what was asked for; a bug that was found is
  pinned down with a test or a check scenario.
- **Not a failure:** no tests on a project that has no tests at all. A check is not necessarily a
  test: running a scenario, calling an endpoint or looking at a row in the database is a check too.
  If the log has no runs at all, that does not yet mean "did not check": the person may have
  checked in another terminal.

### Framing the task

What the person put into the prompt before the agent started, and at what moment.

- **Counts:** context (a fact the agent cannot learn from the repository), references to files and
  functions, exactly one task, targeted constraints ("don't touch this file", "no new
  dependencies"), a plan before code on multi-file work. A frame set up front weighs more than one
  pieced together after "remove that, I didn't ask for it".
- **Does not count:** where the prompt came from. Copied, found or generated by a model makes no
  difference; what matters is that a good prompt is put to work. Constraints moved into the
  project rules file count; they are not treated as a gap. A polite "do it carefully" is not a
  constraint.

### Owning the decisions

Whether the person stayed the author of the decisions once the agent started writing the code.

- **Counts:** questions about the mechanics rather than the status; a refusal with a reason; an
  objection to an architectural move; a reaction to the agent's warning; trimming what is not
  needed; checking an "all done" report; admitting not understanding and then working it out.
- **Does not count:** how often the person steps in. A short "yes" after a frame set in advance is
  ownership; endless renaming while a data schema was accepted silently is not.

### Changing course after failure

What the person does when the result does not fit.

- **Counts:** each next attempt brings a new fact (an error, an input, a constraint); after the
  second failure the lever changes (prompt → test → rule in a file → rollback → new session);
  there is a stop rule; a failed change is rolled back rather than fixed on top.
- **Does not count:** the number of iterations as such: iterating is normal work. Irritation, caps
  lock and exclamation marks do not affect the score.

### Managing context

What the person fills the model's window with, what goes into files and what they do when the
window swells.

- **Counts:** the agent relies on the project rules without reminders; files are supplied in a
  targeted way; topics are not mixed in one session; before a reset the outcome is saved to a file;
  after automatic context compaction the task is restated.
- **Does not count:** the quality of the rules file itself: that would assess an artifact, not the
  logs. If the tool does not report how full the window is, the numeric rules simply do not apply.

### Breaking down the work

How the person slices the work and where each piece goes: the same chat, a new one, a subagent, a
separate terminal.

- **Counts:** one task per round; a check and a commit between tasks; exploration limited to a
  folder and a question; independent pieces run in their own contexts and come together in one
  place.
- **Does not count:** slicing for its own sake. Dictating "open the file, change the function"
  without a definition of done is as much an extreme as doing everything in one prompt.

### Calibrating trust in the agent

Whether trust changes with the cost of a mistake.

- **Counts:** the person treats a migration, a deletion or production data differently from a
  rename; the environment is prepared in advance (a branch, a test database); external facts are
  checked at the source; the reason not to check is said out loud ("reversible, not looking").
- **Does not count:** suspicion of everything. Checking everything in the same detail is no
  calibration either. Switching models because of limits counts only if a property of the task is
  named.

### Keeping changes reversible

How cheap it is to undo a bad move by the agent.

- **Counts:** a return point before a run; a step the size of one unit of work; risky work in a
  branch or a copy; a bad result thrown away whole rather than fixed on top; work starts from a
  clean tree.
- **Does not count:** the number of commits as such. If versioning is not visible in the log, it is
  "insufficient data", not zero: the person may have committed in another terminal. On a small
  solo project branches are often simply not needed.

## Insufficient data: no signal is not a failure

A log does not show everything. The person may have checked the result in another terminal, read
the diff themselves or discussed a decision by voice. Some tools barely record a command trace.

So every axis has an honest answer, **"insufficient data"**. It is given when the behaviour is not
visible in the log and **never turns into a low score**. A low score needs positive evidence: the
log shows a result accepted without a check, or shows there was nothing to roll back to. "Not a
single run in the log" is not such evidence.

The reason for "insufficient data" is recorded as one of eight: log too short, behaviour not seen
in the logs, no context report, no repository access, tool leaves no trace, log truncated, work
happened outside the log, nothing to verify.

If fewer than three axes are scored, the overall level is "insufficient data" too.

## The gate: a ceiling on the overall level

Some moments in a log matter so much that they cap the overall level, however good the rest looks.
This is the gate. It **does not zero** the score, it sets a ceiling, and it reacts only to what
**is** in the log. Silence never triggers the gate.

| Trigger | What it looks like in the log |
|---|---|
| Blind acceptance of a large change (G1) | "ok", "yes", "go ahead" on a change to several files, a schema or dependencies, and not a single sign of ownership in the session |
| Leaving a choice to the agent (G2) | the question needs product knowledge that only the person has, and the decision is handed to the agent ("up to you") without a reason |
| Deaf to a warning (G3) | the agent said "this will break X" or "a migration is needed", and the person's next message ignores it |
| Report accepted without checking (G4) | after "all done" comes the next task right away, with no run, comparison or question |
| Stated confusion left unresolved (G5) | "didn't get it, but ok", "as long as it works", and no follow-up afterwards |
| No stance over a long session (G6) | many turns, a large diff, and not a single refusal, clarification or manual edit |

One trigger caps the level at the middle of the scale ("Competent"), two or more at "Developing".

The gate **does not fire** if a short "ok" follows a frame set in advance, if the question did not
matter (a variable name), if a reason is given ("this is a throwaway script"), if the diff is
small, if it is a sandbox or a prototype, if the result was checked by a tool (the tests were run,
a second agent reviewed it) or if a couple of turns later it is clear the person read everything.

## Levels

Each axis gets a score from 0 to 4 from verbatim quotes, or "insufficient data". From the scored
axes a script computes the overall level: it takes the median, with verifying results counted
twice. Axes with "insufficient data" do not enter the median.

| Level | Median | What it means |
|---|---|---|
| Orchestrator | 3.5 and above | the frame is set before the start, the result is accepted on evidence, the work is sliced by risk |
| Confident driver | from 2.75 | working habits are steady, a few spots are still left without a system |
| Competent | from 2.0 | the basics are in place, but a noticeable share of the decisions goes to the agent |
| Naive | from 1.0 | the agent leads rather than the person, who reacts to breakages |
| Passenger | below 1.0 | the agent's output is accepted with almost no engagement |
| Developing | — | the ceiling when two or more gate triggers fired |
| Insufficient data | — | fewer than three axes scored |

The level is computed by a script by rule, not by a model by feel. The judge gives its own level
only as a cross-check; the reviewer sees any mismatch.

## Anti-patterns

An anti-pattern is a recognisable habit that costs a lot. Each one is tied to one of the axes and
backs up its score rather than living as a separate score. It counts only with a verbatim quote and
only when its main sign is visible. A few examples:

- **Mega-prompt**: five tasks in one message, and the first one is not checked yet;
- **Fix loop**: the third "fix it" in a row with no new fact;
- **Green report taken on faith**: "all tests passed" accepted without the output;
- **Unasked extras**: the agent did more than was asked, and it went unnoticed;
- **No return point**: there is no rollback point, so a failure is fixed on top.

Safety flags are marked separately: a secret in the open, a destructive command without review,
access broader than the task and the like. Only the reviewer sees them; in self mode the reviewer
is the person themselves.

The full list of anti-patterns and flags with their signs and remedies is in the plugin reference
`references/antipatterns.md` (in Russian).

## What the person sees and what they do not

The person gets a text: a short opening, one to three "try differently" items with the place in
the log and a concrete action for the next session, and a walk through all eight axes by their
human names. An axis with nothing visible in the logs is called just that: "Nothing in the logs
shows this." It is not a reproach.

| What | Does the person see it |
|---|---|
| The text with actions and the walk through the eight axes | yes |
| Axis scores | no; in self mode only if `show_scores` is on in `config.json` |
| Overall level | no; in self mode with the same flag |
| A gate that fired, safety flags, the judge's doubts | no, this is the service part for the reviewer |
| Comparison with other people | never, in any mode |

In team and course modes a reviewer reads the text first, and only then does it go to the person.
Logs are voluntary: if there are none, there is no text and no conclusion about the person.
